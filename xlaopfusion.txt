What does XLA do different in terms of fusion from other compilers?

Attach
Assistant Reply:

Here are the main ways XLA’s fusion differs from other ML compilers, based on the analysis in “Operator Fusion in XLA: Analysis and Evaluation” and broader context:

    Rule-based, not search-based
        XLA primarily uses hand-crafted, heuristic rules to decide fusibility (instruction fusion, fusion merger, multi-output fusion, horizontal fusion). It doesn’t perform global search or autotuning for fusion choices on GPU backends (unlike TVM/Ansor, DeepCuts, PET, etc.), which trade compilation time for potentially better fused kernels.

    Conservative “safety-first” criteria
        XLA maintains explicit “do-not-fuse” lists (e.g., convolution, sort, all-reduce) and avoids fusion that may blow up code size, exceed GPU resource limits (registers, shared memory, threads/block), or create nested loops. It rejects multi-user concats and other patterns that could cause code duplication. This tends to reduce fusion opportunities versus more aggressive frameworks.

    Late, vertical fusion focus with distinct passes
        Fusion comes relatively late in XLA’s multi-pass pipeline after canonicalization, layout assignment, and target-specific optimizations. Its vertical fusion variants include:
            Instruction fusion: fuse producers into consumers if ShouldFuse rules pass.
            Fusion merger: merge existing fusion nodes if it won’t increase bytes moved or duplication.
            Multi-output fusion: sibling and producer-consumer MOF to reduce memory reads/writes.
            Horizontal fusion: fuse small, shape-different kernels to grow launch dimensions and cut launch overhead.
        In contrast, systems like TVM may co-design layout/tiling/fusion with a search loop, letting upstream transformations create better fusion opportunities.

    Strict boundaries at custom calls and libraries
        On GPUs, XLA typically treats cuDNN/cuBLAS and other custom-calls (e.g., cuRAND Threefry RNG) as fusion barriers. TPU backends have more end-to-end fusion latitude. Other compilers that generate custom kernels end-to-end (or integrate scheduling around these ops) can sometimes fuse through more of the graph.

    Graph-shape sensitivity from the frontend
        XLA’s fusibility depends strongly on the HLO graph shape produced by the frontend (JAX/TF). Seemingly innocuous Python constructs (like concatenating state for convenience) can block fusion; rewriting code (e.g., passing scalars/arrays directly, using scan/unroll appropriately) often unlocks fusion. Some other compilers employ equivalence-transform passes or search to rewrite graphs to be more fusible automatically.

    No kernel-parameter co-tuning during fusion on GPU
        XLA’s GPU fusion doesn’t integrate autotuning for block sizes/tiling with fusion decisions. Systems like TVM/Ansor or DeepCuts jointly explore fusion choices and low-level schedules to optimize memory traffic and occupancy.

    Multi-output fusion is a first-class optimization
        XLA’s sibling and producer-consumer multi-output fusion (with prioritization rules) is a distinctive, practical middle ground: it reduces memory traffic without going into full schedule search. Some frameworks do less with MOF by default unless guided by tuning.

    Horizontal fusion across shapes
        XLA’s horizontal fusion specifically targets the “many small kernels” phenomenon (e.g., optimizer updates), even when shapes differ. That’s a pragmatic design to reduce launch overhead on GPUs, not universally present in all compilers.

    Limited concurrent-kernel exploitation
        While XLA can compute a breadth-first launch order and recognize potential concurrency, in practice the analysis found limited use of multiple CUDA streams for overlapping fused kernels. Other stacks sometimes more aggressively overlap compute/copies.

In short: XLA emphasizes fast, conservative, rule-based fusion with practical vertical, multi-output, and horizontal strategies, integrates tightly with library calls (which become fusion barriers on GPU), and relies on good frontend graph shapes. Search-based compilers (TVM/Ansor, DeepCuts, PET) push more aggressive, globally coordinated fusion via tuning at the cost of much higher compile times, potentially achieving better peak performance on specific workloads.

how does it compare to what inductor is doing?
Assistant Reply:

Short answer: Inductor is more dynamic, search- and schedule-aware (via Triton and optional autotuning), and fuses “end-to-end” into custom kernels more aggressively than XLA’s conservative, rule-based, library-centric approach on GPU.

Key differences

    Fusion philosophy
        XLA: Rule-based fusibility in HLO with conservative guards (no expensive ops, avoid code-size blowups, multi-user concat barriers, custom-call barriers). Late-stage vertical fusion plus multi-output and horizontal fusion; no global search on GPU.
        TorchInductor: Pattern-driven graph rewriting but geared toward generating new kernels (mostly via Triton on GPU). It aims to fuse broadly across pointwise, reductions, broadcasts, permutes, and many matmul-adjacent patterns, often forming a single Triton kernel per region. It’s less constrained by “don’t-fuse” lists because it owns the generated kernel.

    Libraries vs custom code
        XLA: Heavily relies on library calls on GPU (cuDNN/cuBLAS) which act as fusion barriers; can’t fuse through cuRAND etc. TPU backend is more integrated but on GPU these calls split fusion regions.
        Inductor: Prefers generating Triton kernels for elementwise/reduction-heavy regions; will still call into cuBLAS/cuDNN for heavyweight ops but can often wrap/fuse surrounding epilogues/prologues into Triton kernels, reducing memory traffic.

    Scheduling and autotuning
        XLA: Fusion decisions are not jointly co-optimized with low-level schedules on GPU; launch parameters come from heuristics. No broad autotuning loop for fused kernels.
        Inductor: Triton kernels come with tunable tile/block shapes; Inductor can optionally autotune them per workload/shape. This couples fusion with schedule choices to hit better occupancy/bandwidth.

    Handling dynamic shapes and Pythonic models
        XLA: Works best with static-ish shapes and well-structured JAX/TF graphs; frontend code shape strongly impacts fusibility. Python loops or convenience ops (e.g., concat) can block fusion unless rewritten or unrolled.
        Inductor: Designed for PyTorch eager with dynamic shapes; captures FX graphs at runtime, applies shape-specialization/guards, and generates kernels on the fly. Fusion is resilient to common PyTorch patterns.

    Horizontal and multi-output fusion
        XLA: Has explicit horizontal fusion (fusing small, differently shaped kernels to reduce launches) and multi-output fusion (sibling and producer-consumer) with prioritization rules.
        Inductor: Achieves similar benefits implicitly by forming larger Triton kernels that compute multiple outputs and fuse across branches when profitable; not framed as separate “horizontal/MOF” passes.

    Concurrency and streams
        XLA: Computes a BFS-like launch order and can identify concurrent regions, but practical multi-stream overlap is limited in many cases.
        Inductor: PyTorch runtime more actively overlaps copies/compute when possible; Triton kernels are often heavier and fewer, reducing the need for complex stream choreography.

    Compile time versus peak performance
        XLA: Faster, predictable compilation; conservative fusion to avoid regressions; fewer gigantic kernels; less tuning overhead.
        Inductor: Will spend more compile time (and optional autotuning time) to generate high-performance Triton kernels; often achieves better end-to-end performance for PyTorch workloads, especially on elementwise/reduction-heavy code.

    Ecosystem positioning
        XLA: Best with JAX/TF, TPU-first design heritage; GPU backend is improving but library barriers remain.
        Inductor: Native to PyTorch; Triton gives it strong GPU codegen for custom fused kernels without leaving the PyTorch ecosystem.

When each tends to win

    XLA shines when:
        You’re in JAX/TF with mostly static shapes, benefit from TPU integration, or need very fast compile times with solid baseline fusions.
    Inductor shines when:
        You’re in PyTorch with dynamic shapes, lots of elementwise/reduction glue around matmuls/convs, and can leverage Triton codegen and autotuning to cut memory traffic and kernel launches.

Bottom line
Inductor pushes fusion by generating custom Triton kernels and (optionally) tuning their schedules, enabling broader, performance-oriented fusion on GPUs. XLA focuses on safe, rule-based fusion and leans on vendor libraries, which limits fusion across those boundaries but provides faster, robust compilation.

can you explain the current differences between jax and torch
Assistant Reply:

Here’s a concise, practical comparison of JAX and PyTorch (Torch), focusing on how they feel to use today and where they differ under the hood.

Programming model and UX

    PyTorch
        Eager by default, imperative, Pythonic. Great for debugging and interactive work.
        Autograd is dynamic; graphs are built as you run ops.
        torch.compile (TorchDynamo + AOTAutograd + Inductor) optionally captures graphs and compiles them to speed up models without leaving PyTorch.
    JAX
        Pure functional style encouraged; no in-place mutation, prefer pure functions.
        You opt into transformation primitives: jit, grad, vmap, pmap/pjit, scan, while_loop.
        Feels NumPy-like (via jax.numpy) with automatic differentiation and compilation when you ask for it.

Compilation and fusion

    PyTorch
        Eager path uses many kernels. With torch.compile, it captures FX graphs and generates fused kernels (often Triton) via TorchInductor; can autotune schedules.
        Good at fusing pointwise, broadcasts, reductions; tends to call cuBLAS/cuDNN for matmul/conv but can fuse prologues/epilogues.
    JAX
        jax.jit lowers to XLA HLO and compiles. XLA uses rule-based, conservative fusion (instruction, multi-output, horizontal). On GPU it often treats cuDNN/cuBLAS/custom-calls as fusion barriers.
        TPU backend supports broader end-to-end fusion; GPU backend is improving but remains more library-centric.

Automatic differentiation

    PyTorch
        Reverse-mode autograd by default; rich support for control flow in eager.
        AOTAutograd (under torch.compile) splits forward/backward for better compile-ability and performance.
    JAX
        grad, value_and_grad, jacfwd/jacrev with composable transforms (nest grad with vmap, jit, etc.).
        Emphasis on functional purity makes AD transforms very predictable and composable.

Performance characteristics

    PyTorch
        Eager: quick iteration, sometimes slower runtime.
        torch.compile can deliver large speedups by fusing and generating Triton kernels; optional autotuning can further improve throughput at extra compile cost.
    JAX
        jit can deliver big speedups with ahead-of-time-like compilation; excels when shapes are static or easily specialized.
        Very strong on TPUs; on GPUs, performance is solid but can be gated by XLA’s conservative fusion and library boundaries. Loop unrolling and using scan/while_loop help.

Shapes, control flow, and dynamism

    PyTorch
        Naturally handles dynamic shapes and Python control flow in eager.
        torch.compile adds guards/specializations; many dynamic patterns now compile, but pathological dynamism can cause graph breaks or recompiles.
    JAX
        Prefers static-ish shapes. Dynamic shapes and Python control flow should be expressed with JAX primitives (lax.while_loop, lax.scan, cond) for good compilation.
        vmap/pjit make SPMD-style batching/sharding explicit and powerful.

Parallelism and scaling

    PyTorch
        DDP is the standard for multi-GPU training; FSDP/ZeRO for memory sharding; pipeline/tensor-parallel options via ecosystem libraries.
        Inductor generates GPU kernels; Triton enables performance on custom fused ops.
    JAX
        pmap (device-parallel) and pjit (partitioned sharding via GSPMD) provide concise multi-device parallelism and model/data sharding; very mature on TPU pods.
        SPMD partitioning and sharding annotations are first-class.

Numerics and reproducibility

    PyTorch
        RNG keyed to generators; reproducibility depends on seeding and op determinism settings.
        AMP via autocast/GradScaler; bf16/fp16 widely used; cudnn_deterministic/cudnn_benchmark flags influence perf/determinism.
    JAX
        Stateless, keyed RNG model that composes well across transformations.
        bf16/fp16 well supported; pure-functional style and XLA compilation often yield stable, reproducible behavior when seeds and shapes are fixed.

Ecosystem and libraries

    PyTorch
        Very large ecosystem: vision, audio, text; rich model zoos; ONNX export; widespread production tooling (TorchServe, Triton Inference Server).
    JAX
        Lean core with fast-growing ecosystem: Flax/Equinox for NN modules, Optax/Orbax, haiku, T5X/PAX for large-scale training, Brax for physics, Chex for testing. Strong in research that targets TPU.

Ergonomics and APIs

    PyTorch
        Object-oriented modules (nn.Module), in-place ops, mutable state; approachable for beginners and production engineers.
    JAX
        Functional parameter passing; libraries like Flax/Haiku add module-like ergonomics while keeping functional semantics.

When to choose which

    Choose PyTorch if:
        You need maximal flexibility in eager mode, large ecosystem support, and production tooling; torch.compile can accelerate without significant code changes.
    Choose JAX if:
        You want powerful program transformations (jit/vmap/pjit/grad) in a clean functional style, strong TPU performance/scalability, and are comfortable expressing control flow and parallelism with JAX primitives.

Rules of thumb to get speed in each

    PyTorch
        Try torch.compile(model, mode="max-autotune") on stable code paths; avoid graph breaks; batch small ops; use channels-last/mixed-precision for convs.
    JAX
        Wrap hot paths with jit; use scan/while_loop instead of Python loops; prefer static shapes; avoid unnecessary concats/reshapes that block fusion; consider unrolling small loops; leverage pjit/sharding for multi-device.

Bottom line

    Both can reach high performance. PyTorch aims for dynamic ease-of-use with optional compilation that increasingly closes the gap. JAX aims for composable program transformations and strong compiler-driven performance, especially on TPU. Your workload’s dynamism, target hardware, and team’s preferred programming style usually decide the better fit.

does operator fusion only occur in @jit commands in jax? what are scan/while_loop constructs? give some examples with code

Assistant Reply:

Short answer

    Yes, XLA operator fusion happens when your JAX code is compiled, typically via jax.jit (or higher-level APIs that use jit under the hood).
    Outside of jit, JAX runs eagerly and won’t trigger XLA fusion.
    scan and while_loop are JAX control-flow primitives (from jax.lax) that express loops in a way the compiler understands, enabling fusion and other optimizations.

Details

Where fusion happens in JAX

    Eager (no jit): Ops execute immediately; no XLA HLO is built; no fusion.
    With jit: JAX traces your function to XLA HLO and compiles it; XLA then applies operator fusion (instruction fusion, multi-output fusion, horizontal fusion, etc.).
    Other transforms that compile:
        pmap and pjit also compile via XLA and thus enable fusion inside their compiled regions.
        vmap by itself doesn’t compile; combined with jit (e.g., jit(vmap(...))) it will.

What are lax.scan and lax.while_loop?

    lax.scan: A compiled loop combinator for fixed-structure iteration over a sequence (like functional for/scan). It carries a state (“carry”) across steps and returns both final carry and stacked outputs. It enables efficient compilation, fusion across steps (sometimes with unrolling), and avoids Python-loop tracing overhead.
    lax.while_loop: A compiled while loop with a condition function and a body function, each operating on a loop “carry”. It supports data-dependent iteration counts while staying compilable and fusible.

Why use them?

    They keep control flow inside the XLA graph instead of Python, enabling:
        Operator fusion across loop bodies where profitable
        Fewer kernel launches
        Better memory locality and register reuse
        Much faster compile times versus tracing large Python loops

Code examples

    jit without control-flow primitives (simple elementwise)

python

import jax
import jax.numpy as jnp

@jax.jit
def fused_affine_relu(x, w, b):
    y = x @ w + b
    return jnp.maximum(y, 0.0)

x = jnp.ones((1024, 1024), jnp.float32)
w = jnp.ones((1024, 1024), jnp.float32)
b = jnp.zeros((1024,), jnp.float32)

out = fused_affine_relu(x, w, b)  # Compiled; XLA may fuse add+relu, etc.

    Using a Python loop (don’t do this if you want good fusion)

python

@jax.jit
def bad_loop(x):
    # Python loop gets unrolled at trace time; can bloat HLO or block fusion
    for _ in range(100):
        x = jnp.tanh(x) + 0.1 * x
    return x

Better: use lax.scan or lax.fori_loop.

    scan: iterating over a sequence with carry and stacked outputs

python

from jax import lax

def step_fn(carry, x_t):
    # carry: state carried across steps, x_t: per-step input
    carry = jnp.tanh(carry + x_t)
    y_t = carry * 2.0
    return carry, y_t

@jax.jit
def run_scan(init_carry, xs):
    # xs shape (T, ...). scan returns (final_carry, stacked outputs)
    final_carry, ys = lax.scan(step_fn, init_carry, xs)
    return final_carry, ys

T, D = 1000, 256
init = jnp.zeros((D,))
xs = jnp.ones((T, D))
final_carry, ys = run_scan(init, xs)

Notes:

    scan builds a single compiled loop. XLA can fuse much of step_fn, and may unroll small loops or keep data in registers, reducing kernel launches and memory traffic.

    while_loop: data-dependent iteration

python

def cond_fun(carry):
    x, i = carry
    return (jnp.linalg.norm(x) < 10.0) & (i < 1000)

def body_fun(carry):
    x, i = carry
    x = jnp.sin(x) + 0.01 * x
    return (x, i + 1)

@jax.jit
def run_while(x0):
    carry0 = (x0, jnp.array(0, dtype=jnp.int32))
    x_final, iters = lax.while_loop(cond_fun, body_fun, carry0)
    return x_final, iters

x0 = jnp.ones((1024,))
x_final, iters = run_while(x0)

Notes:

    The loop count depends on data, but the loop is still compiled in one region. XLA can fuse the body operations and minimize kernel overhead.

    fori_loop: fixed-iteration compiled loop

python

def body(i, x):
    return jnp.tanh(x) + 0.1 * x

@jax.jit
def run_fori(x):
    return lax.fori_loop(0, 1000, body, x)

x = jnp.ones((1024,))
y = run_fori(x)

Notes:

    Often preferred for fixed counts; similar benefits to scan for simple loops.

Tips for fusion-friendly JAX

    Wrap hot functions with jit (or pjit/pmap).
    Use lax.scan / lax.fori_loop / lax.while_loop instead of Python loops.
    Avoid unnecessary concats/reshapes that create fusion barriers; pass values separately when possible.
    Keep shapes static or use shape polymorphism carefully; excessive dynamism can hinder optimization.
    Consider unrolling small loops (e.g., via scan with small length or manual unroll) for fewer kernel launches, but balance compile time.

Summary

    Operator fusion in JAX happens when your code is compiled (jit/pjit/pmap). Eager mode won’t fuse.
    scan and while_loop are JAX’s compiled loop primitives that let XLA see and optimize loops, enabling better fusion and performance than Python-level loops.
